# Feature requests — 2026-11-24

Running log of requests received today and what was done for each.

## 1. Add a Stage 1 from the Stage 2's page

**Request:** If we find a Stage 2 and want to add its Stage 1 to the database, can we do
that directly from the Stage 2's page, or do we have to use the admin dashboard's "add a
paper" route?

**Before:** Not possible from the study page. It had to be done in the admin Workflow
(Link step, "Add another item to this group") or Link page.

**Done:**
- New admin-only "Add item" button in the study page's Admin button row (after Edit title, before Link); opens a dialog
  (`src/app/components/AddStudyItem.tsx`, rendered in `src/app/studies/[id]/page.tsx`).
  Pick a role (defaults to whichever of Stage 1 / Stage 2 is missing, else Preprint; works from either side), then search
  the database, paste a DOI (Crossref lookup), or type the metadata manually.
- New mutation `src/app/(admin)/mutations/addPaperToStudy.ts`: resolves/creates the paper,
  links it to the study with the chosen role, approves it, moves it out of any other study
  (deleting that study if emptied), and logs paper edit history.
- Extracted the shared "find or create a paper" logic into `src/lib/addPaperInput.ts`;
  `addPaperToWorkflow` now uses it too (behaviour unchanged).

**Status:** typechecks; not yet tried in the browser.

## 2. Is the queue really sorted by relevance score?

**Question:** The guide says the Queue shows groups "highest relevance score first". Is the
database actually scoring groups by relevance?

**Answer:** No. The queue sorts by `Paper.modelScore`, which is meant to be filled by a
discovery-triage classifier that isn't built yet (see the note above `ModelRun` in
`db/schema.prisma`). Nothing writes `modelScore`, so it is empty for every paper, the Score
column shows "—", and the sort falls back to its second rule, `createdAt` descending (newest
first).

**Done:** Reworded the guide (`src/app/guide/page.tsx`) to "untouched groups, newest first".
The sort code in `src/lib/workflow.ts` and the review page is unchanged, so it will start
ranking by score automatically if a classifier is ever added; the guide line would need
updating then.

## 3. Do user suggestions get checked for duplicates?

**Question:** When users suggest papers, does the database check whether they're already in
it? Is there another place duplicates are checked for confirmed RRs?

**Answer (no code change):**
- Submitting a suggestion (`submitArticleSuggestion.ts`) does no duplicate check; it just
  stores the suggestion. Nothing is added to the papers table at that point.
- The check happens when an admin processes the suggestion (`addSuggestedPaper.ts`): a DOI
  reuses any existing paper with that DOI; with no DOI it reuses only an exact URL match.
  "Find DOI by title" also warns "Something similar is already in the database" (fuzzy
  title match, advisory only).
- Elsewhere: discovery imports skip DOIs / OpenAlex IDs already stored; the admin Link page
  clusters likely duplicates by title similarity so they can be linked into one study or
  marked DUPLICATE; the Add item / workflow add flows reuse a paper with the same DOI or URL.
- Gaps: `Paper.doi` has no database unique constraint (only `openalexId` and Zotero keys
  do), so protection is in code only; a DOI-less suggestion with a different or no URL and
  a differently worded title can slip through to be caught later on the Link page.

**Follow-up (done): stop duplicate DOIs and warn on similar suggestions**
- `Paper.doi` is now unique in the schema (`db/schema.prisma`), via migration
  `db/migrations/20261124000000_paper_doi_unique`. The migration fails if two papers already
  share a DOI, so on production run this first and fix any hits:
  `SELECT lower(doi), array_agg(id) FROM "Paper" WHERE doi IS NOT NULL GROUP BY 1 HAVING count(*) > 1;`
  (the dev database has none). **Not yet applied anywhere**: run `npx prisma migrate deploy`.
  Every discovery import already checks the DOI before creating a paper, so none should trip it.
- New `src/lib/findExistingPaper.ts` (DOI, then link, then fuzzy title).
- Users: `submitArticleSuggestion` now stops a suggestion whose DOI or link is already in the
  database (links to it if public); a merely similar title is flagged with a "submit anyway"
  button. Form: `src/app/suggest-article/SuggestArticleForm.tsx`.
- Admins: the review-suggestion page shows the existing-item warning automatically on load,
  without needing "Find DOI by title".

## 4. Paper page always says "Back to excluded"

**Report:** The back button on an item's page always reads "← Back to excluded", even for
items that aren't excluded.

**Cause:** `src/app/papers/[id]/page.tsx` hardcoded the link to `/excluded`.

**Done:** The link now says "← Back to excluded" (to `/excluded`) only for rejected items,
and "← Back to browse" (to `/`) for everything else.

**Follow-up (done): go back to wherever the user came from.** New client component
`src/app/components/BackLink.tsx`: if the visitor arrived from another page on this site it
calls `router.back()` (so filters/searches are kept); otherwise it follows the fallback link
(`/excluded` for excluded items, `/` otherwise). The label is now just "← Back". Used on both
the item page and the study page.

**Follow-up (done): back-link font size.** Bumped every "← Back to …" link from `text-sm` /
50% opacity to `text-base` / 60% (item, study, suggest-edit, suggest-article, and the admin
pull, review, suggestions and metadata pages).

## 5. Wishlist: live-vs-internal indicators, and how admins move through approval

**Request:** (a) an indicator of which workflow changes go live on the public site vs stay
internal; (b) whether the approval flow should auto-advance a paper to its next step, or
whether it's easier to do many papers in one step at a time.

**Findings (no code change yet):**
- (b) Both approaches already exist. Admin → "One group at a time" follows one group through
  Review → Link → Enrich → Metadata (manual Back / Next step; "Done/Later/Question — next
  group" jumps to the next group). The separate Review / Link / Enrich / Metadata queue pages
  work across all items for bulk jobs. What's missing is auto-advancing to the next *step*
  after finishing a step's action.
- (a) No live-vs-internal indicator exists. Public (live immediately): approving an item
  (status APPROVED shows it on browse), linking items into a study, any metadata/enrichment
  edit, the "verified" badge, rejecting (moves it to the public excluded list). Internal only:
  the Done / Later / Question marker and its note, the queue/in-progress views, review notes.

**Done (both):**
- Live/internal badges: new `workflow/Visibility.tsx` (`LiveBadge` green, `InternalBadge` grey).
  A legend sits under the step bar; each step's intro carries "Live on site"; the Finish bar
  is marked "Internal: marker and note". Also explained in the guide.
- Auto-advance: Review moves to Link once every item is decided and at least one was kept
  (`ReviewStep` `onDone`); saving links moves to Enrich (`LinkStep` `onSaved`). Enrich ->
  Metadata stays manual. Back / Next and the step bar still work.

## 6. Include the original (imported) studies in the workflow queue

**Request:** Only newly discovered articles were in the "One group at a time" queue, not the
original Zenodo/Zotero ones. Can the originals be queued too?

**Cause:** The queue only listed `PENDING_REVIEW` papers. The originals are `IMPORTED`
(1,685 in dev, all already linked into 1,682 studies), so they never appeared.

**Done:** `QUEUE_WHERE` in `src/lib/workflow.ts` now includes `IMPORTED` papers with no
workflow marker. New discoveries still sort first (the sort is newest-created first), then the
originals. The queue count is now study-aware, matching the list. Guide wording updated.
Note: an imported group stays in the Queue until it is marked Done / Later / Question (it
doesn't move to "In progress", which is only for newly approved items).

**Follow-up (done): rename "Clear marker" and keep notes.** Button renamed **Reopen group**
(with a tooltip) in `workflow/FinishBar.tsx`; `setWorkflowMarker` no longer erases the note
when the marker is cleared (it only changes it if edited in the note box). Edit history now
says "Group reopened (workflow marker cleared)". Guide updated.

## 7. Add the Stage 1 from the page of an unlinked Stage 2

**Report:** After unlinking two unrelated items from a Stage 2, its page has no way to add the
Stage 1 (no study, so no "Add item" button). Is it done from this page or the "add papers"
bucket, and would a separately added Stage 1 auto-link to the Stage 2?

**Answer:** Items added separately (e.g. as a suggestion/new paper) are NOT auto-linked: the
new Stage 1 sits unattached in review and the already-reviewed Stage 2 is not sent back to
linking; they only join via Link / the workflow.

**Done:** The **Add item** button now also appears in the Admin row on an item's own page
(`src/app/papers/[id]/page.tsx`). If the item is in a study it adds to that study; if not,
the dialog asks what this item is (guessed from its stage) and what you're adding, creates a
new study holding both, and opens it. Mutation `addPaperToStudy` takes an optional
`anchorPaperId` / `anchorRole` instead of `studyId`. Hidden for excluded items.

**Follow-up (done): make study vs item pages obvious.** Study pages (`/studies/…`) now show a
"Study · N items" badge; item pages (`/papers/…`) show "Single item page", plus (when the
item is in a study) a "view the whole study" button, and for admins a "Not in a study yet"
warning when it isn't linked.
